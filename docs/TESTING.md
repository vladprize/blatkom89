# Testing

## 1. How to run

```bash
npm run typecheck                                   # tsc --strict for shared, server, web, tools
DATABASE_URL_TEST=postgres://…/blatkom_test npm test # unit + integration (each DB test file gets its own schema)
DATABASE_URL=postgres://…/disposable npm run test:e2e # browsers: practice, touch, two-player online, admin
DATABASE_URL=postgres://…/disposable npm run test:e2e:prod # the same against deploy/ in production mode (guest login)
npm run lint && npm run format:check                 # ESLint + Prettier (see §4)
```
`npm run test:e2e` builds the web client, the server bundle and the single-file demo, starts the server
with 40-second matches and runs `tests/e2e/play.mjs`, `touch.mjs`, `online.mjs`, `modes.mjs`, `demo.mjs`
and `gadgets.mjs` (and the rest listed in `run-e2e.mjs`); with `E2E_ADMIN_USER` / `E2E_ADMIN_PASS` it also logs into `/admin`. Screenshots go to
`test-results/e2e/`. The scripts drive the UI by its accessible names and `data-testid`s — mostly the
English UI (`Alias`, `Done`, `Practice`, `Play with Friends`, `Create a room`, `Ready`, `Start`,
`Match report`); `modes.mjs` runs its second browser in Russian (`Кличка`, `Готово`, `К бою!`,
`Протокол матча`, `Быстрый матч`).

Art/UI review helpers (screenshots, not assertions): `tests/e2e/tour.mjs` (fixed camera positions on a
map), `mapshot.mjs` (any map at given points), `ui-tour.mjs` (click through menus), `shot.mjs` (any URL,
optional phone emulation).

## 4. Not verified here

* ESLint / Prettier — could not be installed (npm registry blocked in the build sandbox). `tsc --strict`
  with `noUnusedLocals`/`noUnusedParameters` is the gate that ran.
* Docker image, compose stack, Caddy/HTTPS — no Docker daemon available.
* Inside a real Telegram client (bot + domain needed) and on physical phones — including the v0.3 bot: its
  webhook was exercised over HTTP with fixtures, never by Telegram itself. The v0.2.12 fullscreen, landscape
  lock, safe areas, minimise / return and the account linking through the bot were played by the test's own
  `Telegram.WebApp` object in Chromium (launch data signed with a test token), not by Telegram's iOS / Android /
  Desktop clients — the manual checklist is docs/TELEGRAM.md §5.
* The Mac app on a real Mac — macOS is not available here: the app's code ran in Linux Electron of the same
  version; the bundle is Electron's official macOS release with its own ad-hoc signatures untouched,
  unsigned by a Developer ID and not notarized, so Gatekeeper's first-launch prompt is expected.
* Safari (macOS / iOS) itself — WebKit is not available here. The single file opened from disk in Safari is
  expected to be refused storage (`SecurityError`); that refusal is reproduced in Chromium by the story-offline
  test (the game plays, the story moves on within the session, the hub warns), not observed in Safari.
* The story's balance with real players: the numbers come from a bot playing the hero
  (`npm run story:balance`), a weaker player than most people.
* Team modes with many real players over real networks: capture the flag and base capture were played
  by bots and by two local browsers; their limits (3 captures, 250 points, 15 s flag return, 6 s base
  capture) are first guesses.
* The menu soundtrack is «Hurt» again (v0.2.19, the owner's choice; the file of v0.2.18 part 2, restored
  from git): its licence for use in a game is the owner's to confirm. The game's own «Районные дела»
  (v0.2.18 part 3, `tools/music/`) was checked as a file, not by ear; the owner preferred the phonk.
* Live payments: Xsolla and Stripe were exercised with signed fixtures and a fake HTTP client, Telegram
  Stars against a stand-in for the Bot API (`tests/e2e/fake-botapi.mjs`) — never with a real account or
  real Stars (no provider keys on the live server; the website says «Payments are being connected — coming
  soon»); Resend letters were never sent (no key).
* v0.2.20 on real devices: the iPhone home-screen app's full height (`html.ios-sa`), a match turned sideways
  with the phone's rotation lock on (the turn was played in Chromium with emulated touch: input, results, a tap
  on the turned page), the sprint by the stick, the sideways layouts with a real notch (emulated with insets of
  47 / 47 / 21 px); the full-screen button in Chrome on a Mac in its own full screen (the cause found in the
  code, not on a Mac).
* Full screen on real phones: the corner's button was exercised in Chromium (desktop and an emulated
  Android phone, where the Fullscreen API works) and with an iPhone user agent without the API (the note);
  Safari on an iPhone, the home-screen web app and Telegram's own fullscreen on real clients were not.
* v0.2.21 on real devices: the feel of the aim assist and of the bigger sticks, the frame rate with the zoomed
  HUD, iOS Safari's edge swipe and Android's «back» button against the history guard (played in Chromium by
  the browser's own «back», Playwright's `goBack`), the question on closing a tab mid-match (`beforeunload`; by code — browsers show it only
  after a real gesture), the background loading on a real slow network (Chromium's throttling here).
* v0.2.22's frame rate on real devices: the light-map fix was measured as main-thread time on the stand
  (Chromium with a software GPU, whose own raster speed caps the frame rate there — it stayed at about 23 a
  second); the gain on a real phone's GPU — no texture and framebuffer made and destroyed, no synchronous
  framebuffer check every frame — was not measured on a device.
